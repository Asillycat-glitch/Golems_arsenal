# P2.1b：事件增伤 / 吸收与 Guard 的边界

> 构建：**960,127 B / SHA `B38369B9…8D6` / 2026-11-02 22:09**，已安装。
> 回滚：`mods-backup\golems_arsenal-0.3-testbench-960040-…jar` 等。

## 1. 结论先说

**事件链内的最终写不会吞增伤；事件结束后（tick handler、命令、反射、另一个回调）直接写血仍然会被 Guard 处理。**

判定不是看“谁调用了 setHealth”，而是看**调用栈是否还在伤害/治疗链里**：

- `LivingEntity#hurt` / `m_6469_`
- `LivingEntity#actuallyHurt` / `m_6475_`
- `GuardedEntity#actuallyHurt` / `m_6475_` / `hurtFinal` / `hurtFinalImpl`
- `LivingEntity#heal` / `m_5634_`、`GuardedEntity#heal`
- `ForgeHooks#onLivingHurt` / `onLivingDamage`
- L2 `AttackEventHandler#onActuallyHurtPre/Post` / `onDamagePost`

只要写发生在这个链里、且是**向下写**（`amount <= 当前真值 + EPS`），Guard 就放行，并把
ledger 的 `expected` 直接对齐到这次写入值。这样 Apotheosis / 古遗物 / L2 fin / 本家升级
在事件后段把 amount 改大，不会被 reconcile 回滚。

## 2. 为什么原来可能吞

- 我们的 `LivingHurtEvent` / `LivingDamageEvent` 监听器是 `LOWEST`，通常已经能看到最终值；
  但**同为 LOWEST 的其它监听器**、L2 的 `onDamagePost` / `onDamageFinalized`、以及事件后段
  的 `event.setAmount` 仍可能在我们的监听器之后改 amount。
- 旧的 `allowWrite` 只比较 `amount == expected`，不一致就 `would_block` / `blocked`。
  增伤后的写比对不上，就会被 cancel 或 tick 末回滚。

现在多了一层“事件链写”判定：不依赖我们的监听器是否最后执行。

## 3. 吸收（absorption）也修了

`LivingDamageEvent.amount` 是**吸收之前**的伤害；原来的 `HealthLedger.onDamage` 直接
`expected -= amount`，全吸收的一击没有 `setHealth`，但 expected 已经掉下去，tick 末会把血
“打穿吸收”回滚到低值。

现在：

```text
healthLoss = max(0, eventAmount - absorption)
expected  -= healthLoss
```

全吸收 → `healthLoss=0` → expected 不变；部分吸收 → 只扣真正掉的血。
事件链内的实际写仍会把 expected 对齐到写入口的 amount。

## 4. 仍然会被 Guard 处理的情况

- 命令/测试刺激：`/ga health poke`、`reflect`、`poke_guarded`（栈里没有 hurt/heal）。
- tick handler、AI、任务、网络包回调里直接 `setHealth` / `DATA_HEALTH_ID`。
- 事件**结束后**的额外直接写血（例如在 `LivingDamageEvent` 里 `event.setAmount` 之后，
  又用 `server.execute` 下一 tick 写血）。
- 事件链内的**向上写**（治疗/回血）不走这条豁免；它仍要由 `LivingHealEvent` +
  `lastHealAmount` 解释，避免“伤害事件里顺手满血”成为新后门。
- `readAdditionalSaveData` 仍然走单独的读档收窄，不走这条。

## 5. 对具体 mod 的含义

| 来源 | 典型路径 | 结果 |
|---|---|---|
| 本家升级 / L2 fin | `AttackListener.onHurt/onDamage/finalized` → `hurtFinal` | 事件链内，保留 |
| Apotheosis（神化） | `LivingHurtEvent` / `LivingDamageEvent` 改 amount，或暴击/额外 `hurt` | 事件链内，保留 |
| 古遗物类增伤 | 事件/属性/额外 `hurt` | 事件链内，保留 |
| 事件后 tick 写血 | 直接 `setHealth` | 仍会被拦/回滚 |
| 全吸收的一击 | 无 `setHealth` | expected 不再下降，不会打穿吸收 |

注意：如果某个 mod **在事件里直接 `setHealth` 把血写成更高的值**（治疗），不属于“增伤”，
当前不会自动豁免；需要它走 `LivingHealEvent`，否则仍可能被 Guard 处理。

## 6. 复测

1. **正常 L2 A/A**：同一只傀儡，guard off 与 enforce 各 20 下，`finAvg`/实际掉血应一致，
   `guard(0/0/0)`，无 `[GA-Guard]`。
2. **带增伤的事件武器**：用 Apotheosis/古遗物/本家增伤武器各打若干下，
   guard enforce 与 off 的实际掉血应一致；JSONL 里不应出现这些命中的 `would_block`/`restored`。
3. **吸收**：给 test 傀儡吸收（如 `/effect give @e[type=modulargolems:metal_golem,limit=1,sort=nearest] minecraft:absorption 60 2`），
   打一下；吸收减少、血不应掉，tick 末不应出现 `reconcile restored` 把血打穿吸收。
4. **事件后直接写**：`/ga health poke test 150` 仍应 in enforce 被 `setHealth blocked`；
   `reflect` / `poke_guarded` 仍应被拦。证明豁免只覆盖 hurt/heal 链。
5. **多段/额外命中**：L2 extra hits 或武器多段，每段都应保留；最后一段的 expected 是最终值。

如果出现增伤被回滚，把那条 `kind=guard` 的 `op/decision/caller/notes` 和对应
`l2 finalized` / `living_damage` 的 amount 发我，重点看写入口栈里有没有 hurt 帧。
