## 1. 日志里实际发生了什么

### 1.1 0 血/1 血循环（zero-1，guard=enforce）

ArcaneVortex 的 `HealthModifyHelp.HealthModify#entityDataModify` 和
`EntityKillerHelp#tryInvokeMethod` 反复写 `DATA_HEALTH_ID=0`，还写了一次 `-Infinity`。
我们的 Guard 全部记成 `allowed_lethal`（按设计不拦 `amount<=0`），所以没有阻止 0 血循环。
`tick_max_health` 显示 max 从 1 → 0；此时 `target.health=0, maxHealth=0, dead=true`，
但 Guard 的 `actual` 仍是 **1.0**（旧真值 = `max(synced, guardedData)`，guardedData 还是 1/100）。

### 1.2 真正的 testbench bug：读档时接受了 max=1

zero-1 tick 19155，eid 446（收回后重新放出的同一 UUID）：

```json
{"kind":"guard","op":"max_health","decision":"accepted_build",
 "arg":1.0,"expected":100.0,"actual":1.0,"maxHealth":1.0,
 "notes":"materials/upgrades changed",
 "caller":"net.minecraft.world.entity.LivingEntity#m_7378_:716"}
```

`m_7378_` 就是 `readAdditionalSaveData`。放出的傀儡从 NBT 读到 max=1，`acceptBuildChangeNow`
把这次**读档**当成“换部件”，把 `baseMax` 从 100 改成了 1、expected 改成 1。
从这一刻起 Guard 认为 1/1 是合法的，不再恢复 100；`validateGuardedData` 反复试图写 100，
但被 max=1 夹住（JSON 里 `arg=100, before=1, after=1, max=1, clamped=true`），于是出现
“每个一段时间加 1 血/1 上限”的假恢复。

### 1.3 放出后 1 血、伪死亡

收回时 `toItem` 把当时的 `getHealth()/NBT` 存成 1；再放出时读档写 1。因为 1.2 已经把
`baseMax` 接受成 1，Guard 不再修 max；同时 `GuardedEntity.validateData()` 在
`getHealth()>0` 时会清 `dead`，而 `getHealth()` 走 guardedData 仍可能是 100，
于是出现“dead 被清掉、但实际只有 1 血”的伪死亡。最后 `trulyKill`/death tag 生效时，
持有物里的死亡标记让放出的傀儡直接死亡/消失。

### 1.4 `getHealth` 报告值不可信

同一轮里 `getHealth decision=detected`：

- tick 19155：`synced=1.000 guarded=100.000 reported=1.000`
- tick 19496：`synced=0.000 guarded=1.000 reported=0.000`
- 21:48:41（guard off）：`synced=1.000 guarded=100.000 reported=-213.000`

`reported=-213` 说明这个整合包里 `getHealth` 已经被外部改坏；真值只能取 `DATA_HEALTH_ID`。

## 2. 959021 的修正

1. **真血改为 `DATA_HEALTH_ID`（synced），不再 `max(synced, guarded)`**。
   `guardedData` 只做诊断和“索引缺失兜底”。这样 Guard 在 `synced=1` 时看到的就是 1，
   不会再以为满血。
2. **读档写入不再接受 build 变化**：`allowWrite` 发现 caller 是 `readAdditionalSaveData`
   且 `isLegitSaveLoad()` 通过时，只 `noteBuild()` 记下 build 签名并放行写入，
   **不调用 `acceptBuildChangeNow`、不改 baseMax/expected**。tick 末的 max guard 会按
   原 baseMax（100）尝试恢复 max。
3. **`HealthTrace.start` / 首次 attach 时 `noteBuild`**，避免第一 tick 的 build hash
   变化被 `acceptBuildMax` 当成换部件。
4. **max guard 移到 dead 判断之前**：dead 实体的 max=0/1 也会被修回 baseMax；
   当前血仍然不在 dead 时回滚。
5. 新增 `guarded.data.mismatch` 诊断：`synced` 与 `guardedData` 长期不一致时记一条，
   避免只在 `getHealth` 不一致时才看到。

## 3. 复测这个场景

**前提：必须在攻击前就 `start` + `guard test enforce`**，否则 ledger 没有 100 的 expected，
放出后 attach 会把 expected 设成 1，Guard 没有依据恢复 100。

```text
/ga health guard test enforce
/ga health start p21-av
# 用秘法涡流武器打到 0/1 血
# 收回，再放出
/ga health truth
/ga health report
/ga health stop
```

期望：

- JSONL 出现 `guarded.data.mismatch detected`（synced vs guardedData 不一致）；
- **不再出现** `caller=...m_7378_` 的 `max_health accepted_build`；
- 出现 `max_health blocked`（restoredMax 应为 100），而不是接受 1；
- 放出后 `synced`/`getHealth` 不再长期停在 1；若 expected 仍是 100，应恢复到 100/100；
- 正常 L2、收回、换部件/升级仍不回归。

如果放出后仍然 1 血，先看 `/ga health truth` 的 `synced` 与 `maxHealth`：
- `synced=1, maxHealth=1` 且没有 `max_health blocked` → load 判断没生效；
- `synced=1, maxHealth=100` 且没有 `reconcile restored` → expected 已经被改成 1
  （多半是 trace 中途 stop/start，或读档时 baseMax 已被接受）。

## 4. 仍然是 mod 行为、testbench 不改的部分

- `GuardedEntity.validateData()` 在 `getHealth()>0` 时清 `dead`（伪死亡的来源）。
- `validateGuardedData()` 在 max 被压时反复写 100，被 max 夹住；这是 mod 自己的同步。
- ArcaneVortex 的 `0` / `-Infinity` 写入目前仍按 `allowed_lethal` 放行。要不要在
  `expected>0` 且实体未 dead 时把外部 `amount<=0` 也拦掉，是下一步要决定的事：
  拦了能阻止 0 血锁，但可能让某些绕过事件的死亡路径留下尸体。
- 死亡 tag / 持有物 NBT 是收回/放出链路的 mod 行为，testbench 只能保证 max/health 不被
  错误接受。
