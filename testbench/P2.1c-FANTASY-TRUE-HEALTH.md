# P2.1c：fantasy_ending 真实血量与 guardedData 同步（正式兼容）

> 当前安装：**1,036,114 B / SHA `EA0BA7DF…7488855F` / 2026-11-04 23:40**（sync-only + 正式伤害准入 + fantasy 归一化 + Week 1/2/3/4 + strict + window + combat shadow/action）。
> 978,867 起 fantasy 不再是硬格挡：白名单命中后取消 true damage，用正常伤害源按抗性重结算；
> 未适配的绕过写由正式准入层默认拒绝。详见 [`ARTIFACT-GUARD.md`](ARTIFACT-GUARD.md)。
> **964,165 / 964,449 的负数 clamp 与 auto-recycle 已回滚**：按“梦终剑应该能伤害傀儡、
> 不强行阻止 true damage”的原则，不再在 tick 层和 fantasy 对打。
> 回滚来源：`mods-backup\golems_arsenal-0.3-testbench-963894-…jar`。

## 1. 问题

fantasy_ending 的 `EntityActuallyHurt` 在 `special=true` 时：

1. 先调 `entity.setHealth(...)`（会被 `GuardedEntity.setHealth` 拒绝向下写）；
2. 再用 VarHandle 直接写 `DATA_HEALTH_ID`（真实血量）。

结果：

```text
guardedData = 100
DATA_HEALTH_ID = 70.1
getHealth() = max(70.1, 100) = 100
```

- HUD 显示 70.1/100（或 75/100）；
- `GuardedEntity.heal()` 算 `maxHealth - getHealth()` = 0 → 喂食/回血 no-op；
- `validateGuardedData()` 每 tick 想把 vanilla 顶回 100，被 fantasy 的真实血量层钳回 70.1；
- 看起来就是“梦终武器打掉的伤害不会回复”。

这不是 P2 Guard：zero-3 里 `guard=off`、`guard(0/0/0)`、没有 `blocked`。

## 2. 正式兼容

新增 `compat/fantasy/FantasyTrueHealthCompat`：

- 只在 **fantasy_ending 已加载** 时生效；
- 只处理 **玩家拥有的 `AbstractGolemEntity`**（`getOwnerUUID() != null`）；
- 每 tick 读原始 `DATA_HEALTH_ID`（不走 `getHealth()`），如果
  `getHealth() > raw + 0.001` 连续 **5 tick**，就：
  ```java
  guardedEntity.setGuardedDataImpl(raw, true, false);
  ```
  把 `guardedData` 向下同步到真实血量，并同步给客户端；
- 同步后 `getHealth()`/`heal()` 按真实血量工作，已经打出的伤害不会被“治回去”。

配置（`config/golems_arsenal-common.toml`）：

```toml
[compat]
fantasy_true_health_sync = true
```

P2 Guard 测试建议设 `false`：否则 Guard 在 enforce 下会拦住这次
`setGuardedDataImpl`（amount=raw != expected），两边对打。

## 3. 验证

重启后：

```text
/ga health guard test off
/ga health start p21-fantasy-sync
# 用梦终武器打一下
/ga health truth
```

期望：

- 日志出现 `[Compat] fantasy true-health sync: uuid=... raw=... guarded=...`；
- `/ga health truth` 的 `synced` 与 `guarded` 一致（约等于真实血量）；
- HUD 不再是“100/100 但实际 70”；
- 喂食/回血能正常增加血量；
- 再打一下，raw 再次下降，5 tick 后再次同步。

正常 L2 / 非 fantasy 伤害不应触发 `[Compat]`（`raw == guarded`）。

## 4. 边界

- 5 tick 确认延迟：如果傀儡在这 5 tick 内死亡/被移除，不会同步。
- 只对玩家拥有的傀儡；野生/敌方 golem 不处理。
- `raw > guarded` 时不处理（`getHealth` 已经是 raw）。
- **HEALTH_SEAL 测试**：`/attribute max_health` 把 max 压到 100 时，raw 也会低于
  guardedData；compat 会在 5 tick 后把 guardedData 降到 sealed 值。测 P2 的 max guard
  时请关 `fantasy_true_health_sync`。
- P2 Guard enforce 会拦 compat 的 `setGuardedDataImpl`；要么 guard off，要么关 compat。
- SlashBlade 只是 fantasy 的硬依赖（启动用），不参与血量逻辑。

## 5. fantasy true damage 与“抗性”

> **状态：以下负数 clamp / auto-recycle 已在 963,894 回滚，不再生效。**
> 保留的只有正数 `guardedData` 同步；负数/回收交给 base mod 行为。

zero-7（23:18）里是傀儡地牢的高 max 傀儡（242/235），带：

```text
modulargolems.dungeon_absorption=1
modulargolems.dynamic_reduction=1
modulargolems.damage_cap=1
```

日志里 `living_attack source=fantasy_ending.ds_power n=88 cancelled=88`、
`source=player n=44 cancelled=44`，但血量仍然从 242 一路掉到 **-673**，写入 caller 是：

```text
com.mega.uom.util.entity.EntityActuallyHurt#actuallyHurt0:547
```

结论：**fantasy 的 true damage 不走 LivingHurtEvent / LivingDamageEvent / L2，也不经过
`dungeon_absorption` / `dynamic_reduction` / `damage_cap`**；它直接写 `DATA_HEALTH_ID`，
所以“抗性/吸收”没有机会生效。这不是抗性失效，是伤害绕过了整条抗性管线。

而且它的 true health 没有 0 下限，会写成负数；`GuardedEntity.heal` / `validateGuardedData`
又在负血上循环，HUD 才会出现 `-673/235`。

### 负数夹取（964,165 新增，964,449 已回滚）

`FantasyTrueHealthCompat` 曾计划在读到 `raw < 0` 时：

```java
guardedEntity.setGuardedDataImpl(0.0F, true, false);
```

把 guardedData 夹到 0，让实体按正常死亡流程走，不再让 heal/validate 在负数上循环。
日志：

```text
[Compat] fantasy negative true-health clamped to 0: uuid=... raw=-15.5
```

这只修“负血状态”，**不会**让 dungeon_absorption 挡住 fantasy true damage。要让抗性真正
生效，需要拦截 `EntityActuallyHurt` 的写入（mixin/ASM）或在它之前钳制伤害；那是另一层
compat，风险更高。

## 6. 回收升级（RECYCLE）核实（auto-recycle 已回滚）

Modular Golems 的 `recycle` 是 `GolemFlags.RECYCLE`，只在两个 `hurt` 路径生效：

- `AbstractGolemEntity#hurt` 的虚空掉落；
- `AbstractGolemEntity#postHurt`（由 `GuardedEntity.hurtFinalImpl` 调用）：
  ```java
  if (getHealth() <= 0 && hasFlag(GolemFlags.RECYCLE)) {
      untrack(DEATH_RECYCLE, ...);
      returnToInventory();
      broadcast POOF;
      discard();
  }
  ```

fantasy 的 `EntityActuallyHurt` **不经过 `hurt`/`hurtFinal`/`postHurt`**，所以：

- **recycle 不会触发**，不是“recycle 把傀儡救下”；
- 傀儡会停在负血，`deaths=0`、没有 `DEATH_RECYCLE`；
- 这也解释了为什么带 recycle 的傀儡被梦终剑砍后没有变成持有物。

964,449 新增：`raw <= 0 && hasFlag(RECYCLE)` 时主动执行一次与 `postHurt` 相同的回收：

```java
guardedEntity.setGuardedDataImpl(0, true, false); // 避免 -673 写进 NBT
golem.returnToInventory();
broadcast POOF;
golem.discard();
```

日志：

```text
[Compat] fantasy lethal true-health -> recycle: uuid=... raw=...
```

这样带 recycle 的傀儡被 fantasy true damage 打到 <=0 时会变成持有物，而不是卡在负血；
没有 recycle 的仍然走负数夹 0/正常死亡。

> **注意：上面的 auto-recycle/负数夹取已回滚，964,449 没有这段代码。**

## 7. P2 Guard 的梦终豁免（964,449）

按“梦终剑应该伤害傀儡”的原则，P2 Guard 不再把 `EntityActuallyHurt` 的写入当外部写：

- `HealthTrace.isFantasyHurtCaller()` 识别 caller：
  - `com.mega.uom.util.entity.EntityActuallyHurt`
  - `CatchActuallyHurt0Event`
  - `EntityASMUtil`
- `HealthGuard.allowWrite` 命中时：
  - `markFantasy(uuid, amount)`：把 ledger expected 接受为这次写入值（允许负数）；
  - 设置 5 tick `FANTASY_GRACE`；
  - 直接放行。
- `HealthGuard.allowRemoved` 在 grace 内放行 `setRemoved`，不拦梦终造成的死亡/移除。
- `HealthGuard.reconcile` 在 grace 内：
  - 不做 max/current 回滚；
  - 把 expected 对齐到实际真值（包括负数）；
  - 5 tick 后恢复正常 Guard。

效果：

- ENFORCE 下梦终 true damage **不再被 blocked/restored**；
- 正常的外部写血、`poke`、`reflect` 仍然受 Guard 保护；
- 不做负数夹 0、不强行 recycle。

如果不想让 Guard 豁免，回到 `guard test off` 或去掉 `isFantasyHurtCaller` 分支即可；
这是 testbench-only 的行为，不影响正式内容。
