### 1.3 agent 的结论（21:00 前验证，仍然有效）

- `jdk.attach.allowAttachSelf` 是 **JVM 启动时**读进 saved properties 的，运行期 `System.setProperty` **无效**；失败时 JDK 只抛 `IOException: Can not attach to current VM`（真实原因被吞）。
- 三种路径实测：运行期设属性 ❌；启动 `-D` ✅；**外部进程 attach ✅（不需要任何参数）**。
- 已实现：`AgentBootstrap` 先自 attach，失败回退 `ExternalAttacher`（子进程 attach）。实测日志已出现 `agent=ATTACHED`。
- agent 的 `Scrubber` 会后台遍历类并用 `Field.get` 读静态字段 → **强初始化第三方类**（实测炸在 `RegistrateLootTableProvider.<clinit>`）。按用户决定**不处理**。
- `sanctuary-agent.properties` 现有键：`protect_owned_golems` / `global_ban` / `patch_object_returns` / `verbose` / `violations` / `agent_log`。**没有 scrubber 开关**。

### 1.4 font3d_cache 是什么（别当载荷查）

`<instance>\arcanevortex\font3d_cache\<字体hash>_v2_96\<码点hex>.bin`，3880 个，45MB。
gzip，解压后魔数 `46 33 44 47` = **`F3DG`**，紧跟 `int 2`（版本）+ 码点 + 字形度量/网格。
代码：`Content/Font3D/Client/Font3DGlyphCache.java:34,59-61,86`。**良性，可随便删，自动重建。**
副产物结论：**AV 会往版本目录任意写文件** → 我们的外置记录不能放 `arcanevortex/` 下。

### 1.5 AV 的致命原语全是「自己类里的 PUTFIELD」（2026-11-09 取证，别重新挖）

反编译源码：`%TEMP%\av-src`（1265 个 `.java`，AV jar 0.7.10）。四把武器最后都落到这些
**直接字段写**上，既不在方法边界，也不是反射：

| 文件:行 | 写的是什么 |
|---|---|
| `Help/HealthModifyHelp/HealthModify.java` `entityDataModify` 内 | `var6.f_135391_ = var1`（`DataItem.value`），**在 AV 自己的方法体里直接 PUTFIELD** |
| `Help/EntityKillerHelp.java` `setRemoved` 内 | `var0.f_19864_ = true` → `var0.f_146795_ = var1` → `var0.valid = false` |
| `Content/Item/EntityRemover/RemoveHelp/MainRemove.java:36` | `var0.f_146795_ = RemovalReason.KILLED` |
| `MainRemove.java:51` | `var0.isAddedToWorld = false` |
| `MainRemove.java:240` | `var0.f_146801_ = EntityInLevelCallback.f_156799_`（把 levelCallback 换成空实现） |
| `Content/Item/Sword/FoxBlade/FoxBlade.java:131,138` | `f_19864_ = true`、`m_142687_(KILLED)`（后者是方法调用，mixin 能拦） |
| `Content/Item/VanSh/VanShCrusher.java` `remove` | 同上三件的组合（`f_146795_` + 拆索引 + `onRemovedFromWorld`） |

**结论**：`EntityKillerHelp.remove` 里的 `hurt` / `die` / `setHealth` / `setRemoved` 是走
`tryInvokeMethod` 反射调用的 —— 那些**会**撞上我们的方法门；但上面这些字段写不会。
本项目唯一的字段级拦截 `HealthDataItemSealMixin` 只 redirect `DataItem.setValue` 内部的
putfield，而 **AV 根本不调 `setValue`**，所以它完全无效。

能挡的只有 agent 的 `visitFieldInsn`：按 **owner（写入方类）+ 字段名** 匹配，命中就换成
`GuardRuntime.putField(field, target, value)`，目标不是受保护傀儡就原样写回。
